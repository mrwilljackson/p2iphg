# Dual-ID Pattern: UUID + Airtable Record ID

**Document Version:** 1.0  
**Date:** 2026-02-18  
**Status:** Current Implementation

---

## Overview

The PowerHouseGames Event CRM uses a **Dual-ID Pattern** where every database entity has two identifiers:

1. **Local UUID** (`id`) - Primary key in Neon PostgreSQL database
2. **Airtable Record ID** (`airtableRecordId`) - Reference to corresponding Airtable record

This pattern is essential for the three-phase workflow and enables the system to operate independently during events while maintaining synchronization with Airtable.

---

## Why UUIDs Are Essential

### 1. Local Database Relationships

During the event, relationships must be maintained **within Neon PostgreSQL** without Airtable:

```typescript
// Registration references Organization by local UUID
{
  id: 'reg_abc123',              // Local UUID (primary key)
  organizationId: 'org_xyz789',  // Foreign key to Organization.id (UUID)
  eventId: 'evt_001',            // Foreign key to Event.id (UUID)
  airtableRecordId: null,        // Not yet synced to Airtable
  syncStatus: 'pending',
}
```

**Without UUIDs:** Foreign key relationships couldn't be created during the event because Airtable IDs don't exist yet for new registrations.

### 2. Offline-First Architecture

The system is designed to work **without Airtable** during the critical event period:

- ✅ **With UUIDs:** Create records instantly with local IDs (fast, reliable)
- ❌ **Without UUIDs:** Would need to call Airtable API for every registration (slow, unreliable, network-dependent)

### 3. Idempotency and Sync Safety

UUIDs prevent duplicate records and enable safe retry logic during sync:

```typescript
// Check if already synced before creating in Airtable
if (registration.airtableRecordId) {
  // Update existing Airtable record
  await airtable.update(registration.airtableRecordId, data);
} else {
  // Create new Airtable record
  const airtableRecord = await airtable.create(data);
  
  // Store Airtable ID back in Neon
  await db.update(registration.id, { 
    airtableRecordId: airtableRecord.id,
    syncStatus: 'synced',
    modifiedAt: new Date(),
  });
}
```

### 4. Temporary Database Pattern

Neon PostgreSQL serves as a **temporary cache** that is wiped after each event:

- **Pre-Event:** Import from Airtable (Airtable IDs stored for reference)
- **During Event:** Create new records with UUIDs (no Airtable IDs yet)
- **Post-Event:** Sync to Airtable, then wipe Neon

UUIDs allow the local database to function independently during the event.

### 5. Audit Trail and Debugging

UUIDs provide complete traceability for troubleshooting:

```typescript
{
  id: 'reg_abc123',                    // Local UUID (in logs, errors, admin UI)
  airtableRecordId: 'recXYZ789',       // Airtable ID (for sync verification)
  syncStatus: 'synced',                // Sync state tracking
  createdAt: '2026-03-15T10:30:00Z',   // When created locally
  modifiedAt: '2026-03-15T18:45:00Z',  // When synced to Airtable
}
```

If sync fails, you can identify exactly which records failed by UUID and retry them.

## Three-Phase Workflow

### Phase 1: Pre-Event (Airtable → Neon)

**Purpose:** Import reference data from Airtable to enable fast lookups during event

**Process:**
1. P2I Admin creates Event, Organizations, and Volunteers in **Airtable**
2. Admin clicks "Import from Airtable" button in web app
3. Data is fetched from Airtable API
4. Records stored in **Neon PostgreSQL** with:
   - **Local UUID** (auto-generated by Neon)
   - **Airtable Record ID** (stored in `airtableRecordId` field)
   - All other fields copied from Airtable

**Example - Import Organizations:**
```typescript
// Fetch from Airtable
const airtableOrgs = await airtable('Organizations').select().all();

// Store in Neon with UUIDs
for (const airtableOrg of airtableOrgs) {
  await db.insert(organizations).values({
    // id: auto-generated UUID by Neon (e.g., 'org_xyz789')
    eventId: currentEventId,
    name: airtableOrg.fields['Organization Name'],
    contactEmail: airtableOrg.fields['Contact Email'],
    airtableRecordId: airtableOrg.id,  // Store Airtable ID (e.g., 'recABC123')
    createdAt: new Date(),
    modifiedAt: new Date(),
  });
}
```

**Result:** Organizations are now available in Neon for fast dropdown lookups during registration.

---

### Phase 2: During Event (Neon Only)

**Purpose:** Collect registrations quickly without network dependency on Airtable

**Process:**
1. Attendees register via web form
2. Registrations stored **only in Neon PostgreSQL**
3. No Airtable API calls (fast, reliable)
4. Each registration gets:
   - **Local UUID** (auto-generated)
   - **syncStatus: 'pending'**
   - **airtableRecordId: null** (not yet synced)

**Example - Create Registration:**
```typescript
// User submits registration form
const registration = await db.insert(registrations).values({
  // id: auto-generated UUID by Neon (e.g., 'reg_abc123')
  eventId: 'evt_001',                  // References Event.id (UUID)
  organizationId: 'org_xyz789',        // References Organization.id (UUID)
  attendeeName: 'John',
  attendeeSurname: 'Smith',
  email: 'john.smith@example.com',
  role: 'Participant',
  photoConsent: true,
  syncStatus: 'pending',               // Not yet synced
  airtableRecordId: null,              // Will be set after sync
  createdAt: new Date(),
  modifiedAt: new Date(),
}).returning();

// Returns: { id: 'reg_abc123', syncStatus: 'pending', ... }
```

**Result:** Registration saved locally with UUID. Form submission is instant (no network delay).

---

### Phase 3: Post-Event (Neon → Airtable)

**Purpose:** Sync all registrations to Airtable for long-term storage, then wipe Neon

**Process:**
1. Admin clicks "Sync to Airtable" button
2. App fetches all registrations with `syncStatus: 'pending'`
3. For each registration:
   - Create record in Airtable
   - Airtable returns new record ID
   - Update Neon record with `airtableRecordId` and `syncStatus: 'synced'`
4. Admin verifies sync successful (all records show `syncStatus: 'synced'`)
5. Admin clicks "Wipe Database" button
6. Neon database cleared for next event
7. Airtable remains as permanent source of truth

**Example - Sync Registrations:**
```typescript
// Get all pending registrations
const pendingRegs = await db
  .select()
  .from(registrations)
  .where(eq(registrations.syncStatus, 'pending'));

console.log(`Found ${pendingRegs.length} registrations to sync`);

for (const reg of pendingRegs) {
  try {
    // Create in Airtable
    const airtableRecord = await airtable('Registrations').create({
      'First Name': reg.attendeeName,
      'Last Name': reg.attendeeSurname,
      'Email': reg.email,
      'Event': [reg.eventId],              // Linked record
      'Organization': [reg.organizationId], // Linked record
      'Role': reg.role,
      'Photography Consent': reg.photoConsent,
      // ... other fields
    });

    // Update Neon with Airtable ID
    await db
      .update(registrations)
      .set({
        airtableRecordId: airtableRecord.id,  // Store Airtable ID
        syncStatus: 'synced',
        modifiedAt: new Date(),
      })
      .where(eq(registrations.id, reg.id));

    console.log(`✓ Synced registration ${reg.id} → ${airtableRecord.id}`);

  } catch (error) {
    // Mark as failed for retry
    await db
      .update(registrations)
      .set({
        syncStatus: 'failed',
        modifiedAt: new Date(),
      })
      .where(eq(registrations.id, reg.id));

    console.error(`✗ Failed to sync registration ${reg.id}:`, error);
  }
}
```

**Result:** All registrations are now in Airtable with permanent record IDs. Neon can be safely wiped.

## Dual-ID Pattern Reference Table

| Field | Type | Purpose | When Set | Example Value |
|-------|------|---------|----------|---------------|
| `id` | UUID | Local database primary key | On creation in Neon | `'reg_abc123'` |
| `airtableRecordId` | Text (optional) | Airtable record reference | After sync to Airtable | `'recXYZ789'` |
| `syncStatus` | Text (optional) | Track sync state | On creation / after sync | `'pending'` \| `'synced'` \| `'failed'` |
| `createdAt` | Timestamp | When created locally | On creation in Neon | `'2026-03-15T10:30:00Z'` |
| `modifiedAt` | Timestamp | Last modification time | On creation / update | `'2026-03-15T18:45:00Z'` |

## Database Schema Implementation

All tables in `software/nextjs/lib/db/schema.ts` follow the Dual-ID Pattern:

### Events Table
```typescript
export const events = pgTable('events', {
  id: uuid('id').primaryKey().defaultRandom(),        // Local UUID
  name: text('name').notNull(),
  date: text('date').notNull(),
  location: text('location'),
  description: text('description'),
  status: text('status').notNull(),
  airtableRecordId: text('airtable_record_id'),       // Airtable ID
  createdAt: timestamp('created_at').defaultNow(),
  modifiedAt: timestamp('modified_at').defaultNow(),
});
```

### Organizations Table
```typescript
export const organizations = pgTable('organizations', {
  id: uuid('id').primaryKey().defaultRandom(),        // Local UUID
  eventId: uuid('event_id').notNull().references(() => events.id),
  name: text('name').notNull(),
  isDisabilityGroup: boolean('is_disability_group').default(false),
  // ... other fields
  airtableRecordId: text('airtable_record_id'),       // Airtable ID
  createdAt: timestamp('created_at').defaultNow(),
  modifiedAt: timestamp('modified_at').defaultNow(),
});
```

### Volunteers Table
```typescript
export const volunteers = pgTable('volunteers', {
  id: uuid('id').primaryKey().defaultRandom(),        // Local UUID
  eventId: uuid('event_id').notNull().references(() => events.id),
  email: text('email').notNull(),
  firstName: text('first_name').notNull(),
  lastName: text('last_name').notNull(),
  // ... consent fields
  airtableRecordId: text('airtable_record_id'),       // Airtable ID
  createdAt: timestamp('created_at').defaultNow(),
  modifiedAt: timestamp('modified_at').defaultNow(),
});
```

### Registrations Table
```typescript
export const registrations = pgTable('registrations', {
  id: uuid('id').primaryKey().defaultRandom(),        // Local UUID
  eventId: uuid('event_id').notNull().references(() => events.id),
  organizationId: uuid('organization_id').references(() => organizations.id),
  attendeeName: text('attendee_name').notNull(),
  attendeeSurname: text('attendee_surname').notNull(),
  // ... other fields
  syncStatus: text('sync_status'),                    // Sync tracking
  airtableRecordId: text('airtable_record_id'),       // Airtable ID
  createdAt: timestamp('created_at').defaultNow(),
  modifiedAt: timestamp('modified_at').defaultNow(),
});
```

## Best Practices

### 1. Always Use UUIDs for Primary Keys
```typescript
// ✅ CORRECT
id: uuid('id').primaryKey().defaultRandom()

// ❌ WRONG - Don't use Airtable IDs as primary keys
id: text('id').primaryKey()  // Would break during event
```

### 2. Store Airtable IDs Separately
```typescript
// ✅ CORRECT - Separate fields
id: uuid('id').primaryKey().defaultRandom(),
airtableRecordId: text('airtable_record_id'),

// ❌ WRONG - Using Airtable ID as primary key
id: text('airtable_record_id').primaryKey()
```

### 3. Track Sync Status
```typescript
// ✅ CORRECT - Track sync state
syncStatus: text('sync_status'),  // 'pending' | 'synced' | 'failed'

// Use in queries
const pendingRegs = await db
  .select()
  .from(registrations)
  .where(eq(registrations.syncStatus, 'pending'));
```

### 4. Handle Sync Failures Gracefully
```typescript
// ✅ CORRECT - Catch errors and mark as failed
try {
  const airtableRecord = await airtable.create(data);
  await db.update(registrations)
    .set({ syncStatus: 'synced', airtableRecordId: airtableRecord.id })
    .where(eq(registrations.id, reg.id));
} catch (error) {
  await db.update(registrations)
    .set({ syncStatus: 'failed' })
    .where(eq(registrations.id, reg.id));
  // Log error for manual review
}
```

### 5. Maintain Referential Integrity
```typescript
// ✅ CORRECT - Use local UUIDs for foreign keys
organizationId: uuid('organization_id').references(() => organizations.id)

// ❌ WRONG - Don't use Airtable IDs for foreign keys
organizationId: text('organization_airtable_id')  // Would break relationships
```

## Troubleshooting Guide

### Issue: Sync Fails for Some Records

**Symptoms:** Some registrations show `syncStatus: 'failed'`

**Solution:**
1. Query failed records:
   ```typescript
   const failedRegs = await db
     .select()
     .from(registrations)
     .where(eq(registrations.syncStatus, 'failed'));
   ```
2. Check error logs for specific failures
3. Fix data issues (e.g., invalid email format, missing required fields)
4. Reset `syncStatus` to `'pending'` and retry sync

### Issue: Duplicate Records in Airtable

**Symptoms:** Same registration appears twice in Airtable

**Cause:** Sync was retried without checking `airtableRecordId`

**Prevention:**
```typescript
// Always check if already synced
if (registration.airtableRecordId) {
  // Update existing record
  await airtable.update(registration.airtableRecordId, data);
} else {
  // Create new record
  const airtableRecord = await airtable.create(data);
  await db.update(registrations)
    .set({ airtableRecordId: airtableRecord.id })
    .where(eq(registrations.id, registration.id));
}
```

### Issue: Foreign Key Violations After Database Wipe

**Symptoms:** Error when trying to query registrations after wipe

**Cause:** Database was wiped but some references remain

**Solution:**
1. Always wipe in correct order (child tables first):
   ```typescript
   await db.delete(registrations);  // First (has foreign keys)
   await db.delete(volunteers);
   await db.delete(organizations);
   await db.delete(events);         // Last (referenced by others)
   ```
2. Or use CASCADE delete in schema:
   ```typescript
   eventId: uuid('event_id')
     .notNull()
     .references(() => events.id, { onDelete: 'cascade' })
   ```

### Issue: Can't Find Record by Airtable ID

**Symptoms:** Need to look up record but only have Airtable ID

**Solution:**
```typescript
// Query by airtableRecordId
const registration = await db
  .select()
  .from(registrations)
  .where(eq(registrations.airtableRecordId, 'recXYZ789'))
  .limit(1);
```

## Summary

The **Dual-ID Pattern** is essential for the PowerHouseGames Event CRM architecture:

✅ **Local UUIDs** enable fast, reliable operation during events
✅ **Airtable Record IDs** enable synchronization with long-term storage
✅ **Sync Status** enables safe retry logic and error handling
✅ **Temporary Database** pattern enables cost-effective scaling

This pattern allows the system to be **fast during events** (no network dependency) while maintaining **data integrity** and **long-term storage** in Airtable.
